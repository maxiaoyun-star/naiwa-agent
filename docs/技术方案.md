# 技术方案

## 1. 运行形态

| 层 | 技术 | 说明 |
|---|---|---|
| UI | Kivy 2.3（原生 canvas 手绘） | 不依赖 KivyMD，纯白主题 |
| 打包 | Buildozer + python-for-android | GitHub Actions 云端构建 APK |
| 端侧推理 | llama.cpp（静态编译为 `libnaiwa_llama.so`） | Qwen GGUF，Q4_K_M 量化 |
| 云端推理 | OpenAI 兼容协议（手写 SSE 解析） | 只用标准库 urllib |
| 校园接入 | 自研 CAS 客户端 + 门户适配器 | 只用标准库 |
| 加密 | HMAC-SHA256 派生密钥流 + 认证标签 | 只用标准库 |

**刻意保持依赖极简**：`requirements = python3,kivy`。每多一个原生依赖（cryptography、requests），
就多一个 CI 编译失败点，而这个项目要在 5 天内产出可安装的 APK。所以网络、加密、
HTML 解析全部用标准库重写了一遍——多写 400 行代码，换来构建成功率。

## 3. 一次对话的完整数据流

```
用户输入「明天有课吗」
   │
   ├─ intents.classify → Intent(schedule, scope=tomorrow)
   │
   ├─ tools.schedule
   │     ├─ campus.courses()  → PortalClient._get(课表接口)
   │     │      └─ CookieJar（来自 SessionStore 解密后的会话）
   │     └─ 过滤 weekday=tomorrow → courses_to_text(...)  +  display{groups}
   │
   ├─ prompt.build_messages(user_text, campus_data=数据块, history=最近12轮)
   │
   ├─ router.generate
   │     ├─ 本地可用 → LibNaiwa.generate(ChatML) → 逐 token 回调
   │     └─ 本地失败 → 云端 SSE → 逐 token 回调
   │
   └─ 主线程 Clock.schedule_once 刷新气泡；Reply.display 供列表页渲染
```

关键点：**工具先于模型**。数据在拼提示词之前就已经取到并格式化好了，
模型拿不到"自由发挥"的空间。

## 4. 线程模型

- Kivy 主线程只做 UI；所有网络/推理在 `App.run_bg()` 起的 daemon 线程里跑
- 线程 → UI 的唯一通道是 `Clock.schedule_once(callback, 0)`
- 本地推理对同一模型加了 `threading.Lock`，避免并发 decode 破坏 KV cache

## 5. 安全与隐私

| 数据 | 存放 | 保护 |
|---|---|---|
| 学号 | `session.enc` | SecretBox 加密 |
| 会话 Cookie | `session.enc` | SecretBox 加密 |
| 密码 | 默认**不存**；用户显式开启才存 | SecretBox 加密 |
| API Key | `secrets.enc` | SecretBox 加密 |
| 对话记录 | `history.json` | 明文（可一键清除） |
| 模型文件 | `models/*.gguf` | 明文（公开权重） |

加密方案：`keystream_i = HMAC-SHA256(enc_key, nonce‖i)`，`tag = HMAC-SHA256(mac_key, "NW1"‖nonce‖ct)`，
密钥来自应用私有目录的 32 字节随机文件（0600）。**明确不声称**能对抗 root 或有取证能力的攻击者，
目标是"明文不落盘 + 篡改可发现"。后续版本计划接入 Android Keystore 托管密钥。

## 6. 构建流水线

```
git push
  └─ GitHub Actions
       ├─ job test：python -m unittest（纯标准库，秒级）
       └─ job apk
            ├─ apt 装 buildozer 依赖
            ├─ 缓存 ~/.buildozer（SDK/NDK）
            ├─ scripts/build_llama_android.sh（NDK 交叉编译 libllama.so → libs/arm64-v8a/）
            ├─ buildozer -v android debug
            └─ 上传 artifact naiwa-agent-debug-apk
```

llama.cpp 编译步骤带 `continue-on-error`：编译失败时 APK 仍然产出，
App 自动降级到 API 模式——保证任何时候都有可安装的包。

## 8. Android 13–17 兼容

支持区间：**最低 Android 13（API 33）**，已适配到 Android 17（API 37）。
`buildozer.spec` 里 `minapi = 33`、`api = 36`（compile/target），要跟到 37 只改 `api`。

| 版本变化 | 影响 | 本项目处理 |
|---|---|---|
| 13 (33) 分区存储 | `READ_EXTERNAL_STORAGE` 失效，读不到 `/sdcard/Download` | 只申请 `INTERNET`；模型放 App 私有目录或 `Android/data/<pkg>/files`（均免权限）；不再扫描公共下载目录 |
| 13 (33) 通知权限 | 未声明 `POST_NOTIFICATIONS` 则无法弹通知 | 本版本不发通知，因此不声明 |
| 14 (34) 隐式 Intent 限制 | 隐式跳转需显式包名 | 不使用 Intent 跳转 |
| 15 (35) 强制 edge-to-edge | targetSdk≥35 时界面画到状态栏下 | `platform_compat.insets_dp()` 用 jnius 读 `WindowInsets.Type.systemBars()`，页面 padding 让出安全区；白底配 `LIGHT_STATUS_BAR` 深色图标 |
| 15+ 16 KB 内存页 | 原生库未按 16 KB 对齐会直接崩 | llama.cpp 与 `libnaiwa_llama.so` 统一 `-Wl,-z,max-page-size=16384`，并设 `ANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES=ON` |
| 16 (36) 大屏方向忽略 | 平板/折叠上可能横屏 | 界面全部用相对布局 + 滚动容器，无固定宽高假设 |
| 17 (37) | 延续 35/36 行为 | 同上，无需改动 |

关于 targetSdk 的取舍：Android 15 起 targetSdk≥35 会强制 edge-to-edge，很多人为了省事把
targetSdk 钉在 34。本项目选择直接适配（读真实 insets），因为钉住旧 targetSdk 会逐年变成
「装不上」——Android 每次大版本都会抬高允许安装的最低 targetSdk。

兼容层刻意做成「读不到就返回 0」：jnius 在不同 ROM 上行为有差异，宁可界面紧一点，
也不能因为拿不到系统栏高度而启动崩溃。

## 9. 已知限制

1. **教务接口需手动配置**：门户接口路径无公开文档，必须用本人账号抓包一次。见 `CAS接入说明.md`。
   未配置时 App 明确提示"去配置接口"，而不是报错。
2. **端侧模型能力边界**：2B 模型不适合做复杂推理/长文档，产品上已用"规则接管意图"规避。
3. **未接 Keystore**：见第 5 节。
4. **仅 arm64**：不支持 32 位老机型（2019 年前）。
5. **APK 不含模型**：首次启动需下载 1.19 GB 或手动导入。
